# ng-base — instructions for AI coding agents

## Angular best practices

> Source: Angular CLI 22.2.6 `ng new --ai-config=claude-code` (identical to https://angular.dev/assets/context/best-practices.md), © Google LLC, MIT License. Copied verbatim; the lenne.Tech rules below take precedence where they differ.

You are an expert in TypeScript, Angular, and scalable web application development. You write functional, maintainable, performant, and accessible code following Angular and TypeScript best practices.

## TypeScript Best Practices

- Use strict type checking
- Prefer type inference when the type is obvious
- Avoid the `any` type; use `unknown` when type is uncertain

## Angular Best Practices

- Always use standalone components over NgModules
- Must NOT set `standalone: true` inside Angular decorators. It's the default in Angular v20+.
- Do NOT set `changeDetection: ChangeDetectionStrategy.OnPush` explicitly. `OnPush` is the default in Angular v22+.
- Use signals for state management
- Implement lazy loading for feature routes
- Do NOT use the `@HostBinding` and `@HostListener` decorators. Put host bindings inside the `host` object of the `@Component` or `@Directive` decorator instead
- Use `NgOptimizedImage` for all static images.
  - `NgOptimizedImage` does not work for inline base64 images.

## Accessibility Requirements

- It MUST pass all AXE checks.
- It MUST follow all WCAG AA minimums, including focus management, color contrast, and ARIA attributes.

## Components

- Keep components small and focused on a single responsibility
- Use `input()` and `output()` functions instead of decorators
- Use `model()` for two-way bound properties with `[(prop)]` syntax instead of pairing `input()` with `output()`
- Use `computed()` for derived state
- Use `linkedSignal()` for state derived from multiple reactive sources that must stay synchronized
- Prefer inline templates for small components
- Prefer Signal Forms (`@angular/forms/signals`) for new forms. They are stable in Angular v22+ and provide signal-based state, type-safe field access, and schema-based validation
- When not using Signal Forms, prefer Reactive forms instead of Template-driven ones
- Do NOT use `ngClass`, use `class` bindings instead
- Do NOT use `ngStyle`, use `style` bindings instead
- Do NOT import `CommonModule`, import only the directives and pipes the template uses, such as `AsyncPipe` or `DatePipe`
- When using external templates/styles, use paths relative to the component TS file.

## State Management

- Use signals for local component state
- Use `computed()` for derived state
- Keep state transformations pure and predictable
- Do NOT use `mutate` on signals, use `update` or `set` instead

## Templates

- Keep templates simple and avoid complex logic
- Use native control flow (`@if`, `@for`, `@switch`) instead of `*ngIf`, `*ngFor`, `*ngSwitch`
- Use the async pipe to handle observables
- Do not assume globals like (`new Date()`) are available.

## Services

- Design services around a single responsibility
- Use the `providedIn: 'root'` option for singleton services
- Prefer the `@Service` decorator over `@Injectable({providedIn: 'root'})` for new singleton services (Angular v22+)
- Use the `inject()` function instead of constructor injection

## lenne.Tech rules for this repository

This repository is `@lenne.tech/ng-base`, one of the ten lenne.Tech base repositories: the Angular counterpart of
`@lenne.tech/nuxt-extensions`. Template apps (`ng-base-starter`, generated projects) consume it via npm or vendor it
into `projects/app/src/core/`. A defect found in a project that affects every project is fixed here.

### Layout (contract with the lt CLI vendor mode)

- Workspace as generated by the Angular CLI: library `projects/ng-base` (`sourceRoot: projects/ng-base/src`) and the
  SSR app `projects/playground`.
- Primary entry point: `projects/ng-base/src/public-api.ts` with code in `projects/ng-base/src/lib/**`.
- Secondary entry points `auth`, `ui`, `files`, `share`, `ai`, `sync`, `bug`, `server`, `testing`, `utils`: each is a
  mini library `projects/ng-base/<entry>/ng-package.json` (`lib.entryFile: src/public-api.ts`) with
  `<entry>/src/public-api.ts` and `<entry>/src/lib/**`. Nested entry points follow the same layout one level down:
  `auth/provide`, `ui/provide` and `bug/provide` (providers, guards, auth state, `provideLtUi()`, color mode, bug
  options) keep `app.config.ts` and the route config out of the component layer, `files/ui` holds `<lt-tus-upload>`,
  `bug/server` the bug report middleware. A provider entry point never imports the `ui` barrel nor, not even
  dynamically, the entry that re-exports it (ng-packagr counts `import()` and rejects the cycle).
  The UI theme lives in `projects/ng-base/ui/styles/` and is published as `@lenne.tech/ng-base/ui/styles/theme.css`.
- Code imports another entry point ONLY through the package specifier (`@lenne.tech/ng-base`,
  `@lenne.tech/ng-base/auth` …), never with a relative path across entry points. Inside an entry point imports are
  relative.
- `projects/ng-base/ui/src/lib/helm/**` is generated by `scripts/generate-helm.mjs` from the Spartan CLI templates
  (style vega). Do not edit it by hand; regenerate it.

### Code

- Own components follow `ng g component`: template in its own `.html` file (`templateUrl`), styles only when needed in
  `.css`. This overrides "Prefer inline templates" above. Style guide 2025 file names (`login-page.ts`, no suffix).
- Root services use `@Service()`; per-call state uses `inject…()` factories bound to the injection context
  (`injectLtTusUpload()`, `injectLtAiChat()`, `injectLtOfflineSync()`).
- Every feature is opt-in through a `provideLt…()` function; nothing registers itself.
- SSR safety: never write cookies on the server, never trust the client-writable `lt-auth-state` cookie for anything
  but UI gating, guard browser APIs with `isPlatformBrowser`, build redirect/callback URLs from `NG_PUBLIC_SITE_URL`.
- Every credential is SHA-256 hashed before it leaves the browser (`{ ...params, field: sha256(field) }`).
- Runtime configuration comes from the `NG_*` environment per request (`REQUEST_CONTEXT` on the server,
  `<script id="ng-runtime-config">` in the browser). Never bake values into the bundle.
- Port behaviour from nuxt-extensions, not its bugs; record every deliberate difference in the README.
- Peer dependencies `better-auth` and `@better-auth/passkey` stay in lock-step with nest-server (`>=1.7.16 <1.8.0`).
- Library texts are English in code/JSDoc; user-facing texts come from `projects/ng-base/src/lib/i18n/{de,en}.json`.

### Tests and gates

- Unit tests: Vitest through `ng test`, specs next to the code (`*.spec.ts`). `pnpm test`, filtered:
  `pnpm exec ng test ng-base --no-watch --include='../auth/**/*.spec.ts'` (globs are relative to `projects/ng-base/src`).
- E2E: `pnpm test:e2e` (playground against nest-server-starter on ports 3000/3001), before a release also in
  nest-server's real JWT mode: `NG_BASE_E2E_AUTH_MODE=jwt pnpm test:e2e` (`NSC__COOKIES=false`, same-origin via the
  API proxy). The ports are shared with other stack sessions: ask the holder for a slot, never kill foreign processes.
- `pnpm run check` (auto-fix) / `pnpm run check:raw` (read-only) must pass before a release; `pnpm run check:baseline`
  compares the workspace with a fresh Angular CLI scaffold (release gate and after every `ng update`).

### Git and release

- Base-repo rule: work on the checked-out branch and do not commit unless asked; the release is done via
  `/lt-dev:publish ng-base` (bump, commit, annotated tag `v<version>`, push → `.github/workflows/publish.yml` publishes
  `dist/ng-base` to npm with provenance).
- Version scheme (shared by all base repos, details in `.claude/rules/versioning.md`): MAJOR = Angular major, never
  raised for a breaking change; MINOR = a change an app has to act on when it updates (behaviour, code or
  configuration), always with a migration guide in `migration-guides/`; PATCH = a fix, improvement or addition an app
  takes over as is. `ng-base-starter` always carries the same version; the next release is 22.0.4 (22.0.3 is skipped).
  Keep `package.json`, `projects/ng-base/package.json` and `LT_NG_BASE_VERSION` in sync (`pnpm run version:sync`)
  and update `CHANGELOG.md`.
