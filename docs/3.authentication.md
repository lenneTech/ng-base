Authentication runs through Better Auth on nest-server (`/iam/*`). The auth state lives in two places that share the
same signals:

- **`LtAuthStore`** (`@lenne.tech/ng-base/auth/provide`): user, session check, sign-out. Enough for an app shell that only
  shows the user or signs out. It carries no Better Auth, 2FA or passkey code.
- **`LtAuthService`** (`@lenne.tech/ng-base/auth`): everything of the store plus sign-in and sign-up, 2FA, passkeys,
  password and e-mail flows. Better Auth is loaded on first use. It belongs on the pages that need it.

## In short

```ts
protected readonly auth = inject(LtAuthService);

await this.auth.signIn.email({ email, password }); // password is SHA-256 hashed before it leaves the browser
await this.auth.signIn.social({ provider: 'microsoft', callbackURL: '/auth/callback' });
this.auth.user(); // signal
this.auth.isAdmin(); // computed signal, a UI gate only
await this.auth.twoFactor.verifyTotp({ code }); // sets the user on success
await this.auth.authenticateWithPasskey(); // WebAuthn with the nest-server challengeId
await this.auth.signOut(); // also flushes and wipes offline data when provideLtSync() is active
```

Pass the raw form value: the service hashes every credential itself. Never hash it a second time.

## Guards

| Guard                  | Use                                                                                                  |
| ---------------------- | ---------------------------------------------------------------------------------------------------- |
| `ltAuthGuard`          | `canActivate` of routes for signed-in users                                                          |
| `ltGuestGuard('/app')` | Sign-in pages; a signed-in user goes to the given path                                               |
| `ltRoleGuard('admin')` | Routes for a role                                                                                    |
| `ltSystemSetupGuard`   | `canActivateChild` of the root route; sends every visit to the setup page while the API has no admin |

The guards read the `lt-auth-state` cookie, which the browser can change. They gate the UI only; the API authorizes
every request. Do not build security decisions on `isAdmin()`.

At app start `validateSession()` checks that cookie against `GET /iam/get-session`. When the API answers that no
session exists (401, 403, or neither user nor session), the user in the cookie is signed out, so the app no longer looks
signed in after the session expired on the server. The page stays; the next request that fails with 401 and the next
navigation to a guarded page lead to the login page. A timeout or an error keeps the user, and so does JWT mode with a
stored JWT.

`HttpClient` calls to the API need `ltAuthInterceptor` in `provideHttpClient(withInterceptors([...]))`. Plain `fetch`
calls use `inject(LT_FETCH)`, which adds the cookie or JWT handling.

## Cookie and JWT mode

- **Cookie mode** (default): the session is the API's cookie. When the API offers JWTs, the app also holds one in
  `lt-jwt-token` for its own requests.
- **JWT mode** (nest-server with `cookies: false`, env `NSC__COOKIES=false`): a JWT in a sign-in, 2FA or passkey answer
  switches the store to JWT mode. A JWT that expires within 60 seconds is renewed with itself as bearer before it is
  sent, because nest-server's JWTs live 15 minutes and there is no cookie to mint a new one. Before nest-server 12.7.0
  the browser must reach the API same-origin in this mode (`NG_PUBLIC_API_PROXY=true`).
- **An API without JWT is not asked for one.** When `GET /iam/features` reports `jwt: false`, no request goes to
  `/iam/token`; the app stays on the cookie session.

`lt-jwt-token` holds a JWT or nothing. Never store a token yourself:

- After 2FA, a passkey or a social sign-in the service puts the session in place. `authenticateWithPasskey()` returns
  `{ success, error?, user? }`; `twoFactor.verifyTotp()`, `verifyBackupCode()` and `signIn.social()` drop Better Auth's
  opaque session token from their answer.
- `twoFactor.enable()` / `disable()` and `changePassword({ revokeOtherSessions: true })` replace the session (from
  nest-server 12.11 a JWT is bound to its session) and take the new JWT themselves.
- `setUser(user)` without a mode keeps the transport for the same user, for example after switching 2FA on.

## Sign-in through a social provider

`LtAuthService.signIn.social(params)` signs in through a provider the API configures (`betterAuth.socialProviders` in
nest-server), for example Microsoft Entra ID. `GET /iam/features` lists the enabled providers as `socialProviders`, and
`auth.features()` holds that answer. From nest-server 12.11.0 the answer also carries `emailAndPassword`: when it is
`false`, the API signs in through a provider only, and a login page can hide its e-mail form.

```ts
// login page
protected readonly auth = inject(LtAuthService);
protected readonly providers = computed(() => {
  const value = this.auth.features()['socialProviders'];
  return Array.isArray(value) ? value : [];
});

// The provider shows its account picker. Relative URLs become <NG_PUBLIC_SITE_URL>/…
protected signInWith(provider: string): Promise<LtAuthResponse> {
  return this.auth.signIn.social({ additionalParams: { prompt: 'select_account' }, callbackURL: '/auth/callback', errorCallbackURL: '/auth/login', provider });
}
```

```ts
// auth/callback page (no ltAuthGuard: the user is not loaded yet, the API has just set the session cookie)
constructor() {
  afterNextRender(async () => {
    const signedIn = await this.auth.validateSession();
    await this.router.navigateByUrl(signedIn ? '/app' : '/auth/login', { replaceUrl: true });
  });
}
```

- **Redirect** is the usual way: the browser goes to the provider, which sends it to the API; the API sets the session
  cookie and redirects to `callbackURL`.
- **ID token**, for an app inside a host that already knows the user (Microsoft Teams, a native shell): with `idToken`
  the API answers at once, without navigation. From nest-server 12.11.0 the provider needs
  `disableIdTokenSignIn: false`.
- **Silent attempt:** `additionalParams: { prompt: 'none' }`. With a session at the provider the user is signed in,
  otherwise the provider answers through `errorCallbackURL` with `?error=login_required`. Try at most once per tab, and
  never after an explicit sign-out.
- **`?error=`** carries a code from the provider or Better Auth (`access_denied`, `signup_disabled`, …). Map it to your
  own text. Never render `error_description` or anything else from the query: anybody can put text there.
- **`callbackURL`, `errorCallbackURL` and `newUserCallbackURL` are fixed app paths**, never user input. Relative values
  become absolute on `NG_PUBLIC_SITE_URL`; the API's `trustedOrigins` checks absolute ones.

**An inline profile photo is not kept in the auth state.** Microsoft stores the photo in `user.image` as a `data:` URL,
which would push the `lt-auth-state` cookie past the browser's limit of 4096 bytes. The browser drops such a cookie
without an error, and the next page load looks like a sign-out. So `user().image` is `undefined` for such a user. Read
the photo from the session answer (`(await auth.getClient()).getSession()`), or set `disableProfilePhoto: true` on the
provider in the API.

## Auth mails

Redirect URLs in password-reset and verification mails are absolute app URLs built from `NG_PUBLIC_SITE_URL`
(`LtAuthService.absoluteAppUrl()`), never from user input or the request.
